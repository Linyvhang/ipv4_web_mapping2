# IPv4 Web Mapping 智能体技术栈方案

## 1. 文档目的

本文档根据《产品设计方案》确定智能体分析模块的技术选型、组件职责、部署方式和后续扩展方向，作为后续开发和团队协作的技术依据。

当前技术方案优先服务于第一版 MVP：

- 单个 IP 资产分析；
- 多个 IP 批量分析；
- 异步任务和任务状态查询；
- 标准 JSON 分析结果；
- 批量汇总报告；
- 自然语言查询已有分析结果；
- 只读数据工具；
- 暂定接入通义千问模型。

## 2. 总体技术栈

```text
Python 3.11
├── FastAPI              API 服务
├── LangGraph            Agent 工作流编排
├── Pydantic v2          输入输出模型和 JSON Schema
├── SQLAlchemy 2.x       数据访问层
├── Alembic              数据库迁移
├── MySQL 8              业务数据和分析结果
├── Redis                消息队列、缓存和任务协调
├── Celery               异步任务 Worker
├── httpx                异步模型 API 调用
├── Jinja2               简单结果预览
├── pytest               测试
└── Docker Compose       本地和云服务器部署
```

## 3. 组件职责

### 3.1 Python 3.11

Python 是项目统一开发语言。新开发的智能体模块建议使用 Python 3.11，现有 L1/L2/L3 扫描模块暂不强制重写。

选择原则：

- 使用稳定的类型标注能力；
- 兼容 FastAPI、Pydantic、LangGraph 和 SQLAlchemy；
- 方便在云服务器 Linux 环境部署；
- 避免第一版引入过新的实验性运行时。

### 3.2 FastAPI：API 服务层

FastAPI 负责：

- 创建单 IP 分析任务；
- 创建批量分析任务；
- 查询任务状态；
- 重试和取消任务；
- 查询标准 JSON 结果；
- 提供自然语言查询接口；
- 为可视化模块提供接口。

建议接口方向：

```text
POST /api/tasks/ip-analysis
POST /api/tasks/batch-analysis
GET  /api/tasks/{task_id}
POST /api/tasks/{task_id}/retry
POST /api/tasks/{task_id}/cancel
GET  /api/analysis/{analysis_id}
POST /api/chat/query
```

FastAPI 只负责请求、参数校验、任务创建和结果查询，不在 HTTP 请求线程中执行完整的大模型分析。

### 3.3 LangGraph：Agent 编排层

LangGraph 负责组织多步骤分析流程：

```text
读取 IP 数据
    ↓
整理服务指纹
    ↓
资产类型分析
    ↓
风险分析
    ↓
证据整理
    ↓
生成结构化 JSON
    ↓
保存分析结果
```

LangGraph 适合处理：

- 多步骤分析；
- 工具调用；
- 任务状态；
- 失败恢复；
- 批量子任务；
- 后续人工审核和历史对比。

数据库查询、统计计算和产品归一化等确定性逻辑不应全部写成模型节点，应保留为普通 Service 或只读 Tool。

### 3.4 Pydantic v2：数据契约层

Pydantic 用于定义和校验：

- API 请求模型；
- 任务状态模型；
- 资产画像模型；
- 风险结果模型；
- 标准 JSON Schema；
- 批量汇总报告模型。

示例：

```python
class RiskFinding(BaseModel):
    level: Literal["info", "low", "medium", "high", "critical"]
    title: str
    description: str
    evidence: list[str]
    confidence: float
    recommendations: list[str]
```

Pydantic 模型应作为 FastAPI 参数校验、模型输出校验和可视化接口协议的共同来源。

### 3.5 MySQL 8：持久化数据库

继续使用当前项目的 MySQL 8，不因引入智能体而更换数据库。

智能体模块建议新增以下表：

```text
agent_task
agent_task_item
agent_analysis_result
agent_report
agent_prompt_version
```

推荐关系：

```text
agent_task
 ├── agent_task_item
 │    └── agent_analysis_result
 └── agent_report
```

MySQL 保存：

- 任务记录；
- 子任务状态；
- 标准 JSON 分析结果；
- 批量汇总结果；
- 报告内容；
- 模型和 Prompt 版本；
- 错误和审计日志。

### 3.6 SQLAlchemy 2.x + Alembic：数据库访问和迁移

Agent 新模块建议使用 SQLAlchemy 2.x 的异步 API，并使用 Alembic 管理数据库迁移。

推荐关系：

```text
SQLAlchemy 2.x
    ↓
aiomysql
    ↓
MySQL 8
```

现有扫描模块中的 `aiomysql` 和手写 SQL 暂时保留，不要求一次性重写。新模块先建立清晰的 Repository 层，后续再逐步统一访问方式。

### 3.7 Redis + Celery：异步任务系统

产品需要支持：

- 异步任务；
- 批量子任务；
- 任务状态；
- 失败重试；
- 任务取消；
- 任务队列；
- 多 Worker 扩展。

推荐结构：

```text
FastAPI
    ↓
Redis Broker
    ↓
Celery Worker
    ↓
LangGraph 分析流程
```

Redis 负责队列、短期状态、缓存和 Worker 协调；MySQL 负责保存最终任务和分析结果。

不建议将 FastAPI `BackgroundTasks` 作为正式的长期任务方案。它可以用于早期本地验证，但正式部署应使用独立 Worker。

本地 Windows 开发建议使用 Docker 或 WSL；云服务器建议使用 Linux Worker 环境。

### 3.8 模型适配层

第一版暂定使用购买 Token 的模型服务，模型暂定为通义千问。模型型号确定后再接入具体 SDK 或 API。

LangGraph 不应直接绑定具体模型，应通过统一的 Provider 接口调用：

```python
class ModelProvider(Protocol):
    async def generate_structured(
        self,
        prompt: str,
        output_model: type[BaseModel],
    ) -> BaseModel:
        ...
```

第一版 Provider：

```text
QwenModelProvider
```

后续 Provider：

```text
CloudApiModelProvider
MockModelProvider
```

模型适配层统一负责：

- API 调用；
- 超时；
- 重试；
- 限流；
- 结构化输出；
- 模型错误转换；
- 模型元信息记录。

### 3.9 httpx：模型 API 客户端

使用 `httpx` 进行异步 HTTP 调用，避免阻塞 FastAPI 或 Worker 的事件循环。

模型供应商确定后，可在 Provider 内部使用官方 SDK，但业务层不能直接依赖供应商 SDK。

### 3.10 Jinja2：简单结果预览

第一版可以使用 FastAPI + Jinja2 提供一个简单的结果预览页面，展示：

- IP 摘要；
- 资产类型；
- 风险等级；
- 服务列表；
- 风险列表；
- 证据和建议；
- 任务状态。

该页面只用于开发调试和演示，不替代其他同学负责的正式可视化模块。

### 3.11 pytest：测试和评估

测试框架建议使用：

```text
pytest
pytest-asyncio
httpx
FastAPI TestClient
```

测试范围：

- JSON Schema 校验；
- 风险等级校验；
- 置信度范围校验；
- 数据不足时的输出；
- 只读工具行为；
- IP + scan_round 结果复用；
- API 任务创建和状态查询；
- 失败重试和任务取消；
- 批量任务部分失败；
- Mock 模型输出；
- 模型 Provider 错误处理。

真实模型调用只用于少量集成测试，单元测试不得依赖真实 Token。

### 3.12 Docker Compose：本地和云端部署

第一版建议使用 Docker Compose 组织：

```text
api       FastAPI 服务
worker    Celery Worker
redis     Redis
mysql     MySQL（已有数据库可替换为外部服务）
```

这样可以保证本地开发和云服务器部署使用接近的环境。

## 4. 数据和结果边界

### 4.1 智能体只读工具

第一版允许的工具：

```text
get_latest_scan_summary()
get_asset_profile(ip)
get_service_fingerprint(service_id)
get_asset_history(ip)
search_assets_by_product(product, version)
get_service_statistics(scan_round)
get_risk_statistics(scan_round)
compare_scan_rounds(round_a, round_b)
generate_scan_report(scan_round)
```

第一版禁止的工具：

```text
scan_host()
scan_port()
brute_force()
exploit_service()
```

不提供任意 SQL 工具，只允许调用固定的白名单查询工具。

### 4.2 结果保存

分析结果采用：

```text
固定任务字段 + 标准 JSON 结果字段
```

结果复用依据：

```text
IP + scan_round
```

建议同时记录：

```text
model_provider
model_name
model_version
prompt_version
schema_version
```

不保存大模型未经处理的原始返回内容，只保存经过 Pydantic 校验后的 JSON 结果和必要任务日志。

## 5. 标准 JSON 接口

智能体与可视化模块之间使用版本化 JSON：

```json
{
  "schema_version": "1.0",
  "analysis_id": "analysis-001",
  "ip": "1.2.3.4",
  "scan_round": 1,
  "scan_time": "2026-10-29T10:00:00Z",
  "summary": {
    "asset_type": "Web服务器",
    "risk_level": "medium",
    "description": "该 IP 发现 Web 服务，存在需要进一步关注的版本风险",
    "confidence": 0.86
  },
  "asset_types": [],
  "services": [],
  "risks": [],
  "evidence": [],
  "recommendations": [],
  "limitations": [],
  "metadata": {
    "model_provider": "暂定",
    "model_name": "暂定通义千问",
    "model_version": "暂定",
    "prompt_version": "1.0"
  }
}
```

产品名称和版本需要同时保存原始值和归一化值：

```text
raw_product_name
raw_version
normalized_product_name
normalized_version
normalization_confidence
normalization_evidence
```

归一化策略：程序规则优先，大模型处理复杂情况，无法确认时标记为 `unknown`。

## 9. 暂不建议引入的组件

第一版暂不引入：

- 向量数据库；
- 多智能体协作框架；
- Kafka；
- Kubernetes；
- 复杂权限系统；
- 自动漏洞验证框架；
- 大型前端框架；
- 复杂 PDF 生成系统。

原因是第一版应优先跑通：

```text
L3 数据读取
    ↓
单 IP 分析
    ↓
标准 JSON
    ↓
异步任务
```

## 10. 推荐开发顺序

1. 确定 Agent 任务表和分析结果表；
2. 使用 Pydantic 定义标准 JSON Schema；
3. 编写 L3 数据查询和整理层；
4. 实现产品名称和版本归一化；
5. 实现单个 IP 分析流程；
6. 接入 ModelProvider 和暂定模型；
7. 实现 LangGraph 工作流；
8. 增加风险、证据和置信度校验；
9. 实现 FastAPI 任务接口；
10. 接入 Redis 和 Celery Worker；
11. 实现重试、取消和结果复用；
12. 实现批量分析和汇总报告；
13. 实现自然语言查询；
14. 实现简单 JSON 预览页面；
15. 编写单元测试、接口测试和模型评估样本；
16. 与正式可视化模块联调；
17. 再扩展历史对比和第二条模型路线。

## 11. 选型原则

- 原始扫描数据与 Agent 分析结果分离保存；
- FastAPI 负责接口，Celery 负责长任务；
- LangGraph 只编排复杂分析流程，不替代普通业务代码；
- 统计数字由程序计算，模型负责解释；
- 大模型输出必须经过 Pydantic 校验；
- 智能体只使用只读白名单工具；
- JSON 接口和字段必须版本化；
- 模型供应商通过 Provider 隔离；
- 结果记录扫描批次、模型和 Prompt 版本；
- 任何功能改动都必须补充测试并创建 Git commit。
